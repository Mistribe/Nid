# Subscription Tracking — Data Model

This document describes the data model used to register subscriptions and track their cost over time. It is the reference for implementation: entities, rules, derived computations and how real-world offers map onto the model.

## Goals

- Register any kind of subscription offer: simple recurring billing, prepaid multi-year terms, bonus months, bundles that include subscription time, gift cards, trials, intro promotions, price changes.
- Know at any date whether a subscription is covered, until when, and what the next charge will be.
- Compute cost two ways: **cash cost** (what left the account, and when) and **amortized cost** (what each month of service actually cost).

## Core principle

A subscription is described by three separate concepts that must never be mixed in the same record:

1. **Subscription**: the long-lived relationship with a service (identity, owner, users). It survives renewals, price changes and plan switches.
2. **Money**: what was paid, by whom, and when. Stored as `BillingPhase` (recurring rules) and `Purchase` (one-off payments).
3. **Coverage**: the periods during which the service was accessible, and why (paid, bonus, included, trial, gift). Always **derived**, never entered by hand.

One payment can grant several coverage periods (paid + bonus), and one coverage period can come from a purchase that is not a subscription at all (a game expansion including 1 month). This separation is what makes all the offer variations fit the same model.

## Conventions

- **Dates** are calendar dates (`YYYY-MM-DD`). Intervals are **half-open** `[start, end)`: `end` is the first day *not* covered. Never use inclusive end dates.
- **Durations** are `{ count, unit }` with `unit` in `day | week | month | year`. No enum like `monthly`/`quarterly`/`custom`: "every 4 months" is `{ count: 4, unit: "month" }`. Durations are never converted to a number of days, because months vary in length.
- **Month arithmetic** keeps an anchor day and clamps to the end of the month: starting on Jan 31, +1 month = Feb 28 (or 29), +2 months = Mar 31.
- **Money** is `{ amount, currency }` with `amount` as a decimal type (never floating point) and `currency` as an ISO 4217 code. Amounts are stored in their original currency; conversion only happens at reporting time, using the rate at the payment date.
- **Negative amounts** are allowed only on `adjustment` and `refund` purchases.

## Entities

### Subscription

Stable identity of a service relationship.

| Field | Type | Notes |
|---|---|---|
| `id` | id | Unique. One subscription per service relationship, not per period. |
| `provider_key` | string | e.g. `s_spotify` |
| `name` | string | Display name, e.g. "Spotify Premium Duo" |
| `owner` | `{ type: personal \| family, id }` | Who the subscription belongs to |
| `service_users` | `[user_id]` | Who actually uses it |
| `auto_renew` | bool | Whether open billing phases keep generating charges |
| `cancelled_at` | date? | After this date, no new charges are generated. Existing coverage runs until its end. |

A price change, a plan upgrade or a renewal does **not** create a new subscription. Switching to a genuinely different service (e.g. moving from Spotify to Deezer) does.

### BillingPhase

A recurring pricing rule: "while this phase is active, each renewal costs X and covers N units".

| Field | Type | Notes |
|---|---|---|
| `id` | id | |
| `subscription_id` | id | |
| `starts_on` | date | First possible charge date |
| `ends_on` | date? | `null` = still running. A price change closes the current phase and opens a new one. |
| `price` | money | Price of one renewal |
| `every` | duration | Billing period, e.g. `{1, month}` |
| `covers` | duration? | Coverage granted per renewal. Defaults to `every`. |
| `max_cycles` | int? | Limits the number of renewals (intro offers: "3 months at 0.99"). |
| `payer` | `{ type, id }` | Who pays |

Phases of the same subscription must not overlap in time.

**Important:** a phase does not charge on a fixed calendar. It charges **when coverage runs out** (see "Timeline algorithm"). This is what lets gift cards, bonus months and prepaid terms push back the next charge.

### Purchase

A single payment that is not generated by a phase.

| Field | Type | Notes |
|---|---|---|
| `id` | id | |
| `date` | date | Payment date |
| `label` | string | e.g. "NordVPN 2-year plan", "The War Within Epic Edition" |
| `price` | money | Total paid. `0` for a received gift. |
| `payer` | `{ type: personal \| family \| external, id? }` | `external` = someone outside the household (received gift) |
| `kind` | enum | `prepaid_term \| bundle \| gift \| adjustment \| refund` |
| `grants` | `[Grant]` | Coverage granted by this purchase (may be empty for adjustments/refunds) |
| `allocated_amount` | decimal? | For `bundle` only: part of the price counted as subscription cost. Defaults to `0` for bundles, to `price` for other kinds. Must be `<= price`. |

#### Grant

| Field | Type | Notes |
|---|---|---|
| `subscription_id` | id | |
| `duration` | duration | Length of the granted coverage |
| `source` | enum | `paid \| bonus \| included \| trial \| gift` |
| `starts_on` | date? | Explicit start. `null` = **stack** after the current coverage end (see below). |

### CoveragePeriod (derived)

Never stored as input. Rebuilt from phases and purchases; may be cached.

| Field | Type | Notes |
|---|---|---|
| `subscription_id` | id | |
| `start`, `end` | date | Half-open interval |
| `source` | enum | `paid \| bonus \| included \| trial \| gift` |
| `origin` | `{ phase_id, cycle }` or `{ purchase_id, grant_index }` | Traceability back to the money |

### Charge (derived)

One occurrence of money leaving the account. Purchases are charges as-is. Phases produce one charge per renewal.

| Field | Type | Notes |
|---|---|---|
| `date` | date | |
| `price` | money | |
| `payer` | `{ type, id }` | |
| `origin` | `{ phase_id, cycle }` or `{ purchase_id }` | |
| `coverage` | `[CoveragePeriod]` | Periods this charge paid for (used for amortization) |

## Timeline algorithm

Builds coverage periods and charges for one subscription.

1. Collect the subscription's phases and the grants of all purchases that reference it.
2. Walk time forward, keeping `coverage_end` = end of the last coverage period built so far (initially none).
3. **Grants**, processed in order of their purchase date:
   - If `starts_on` is set, the period is `[starts_on, starts_on + duration)`.
   - If `starts_on` is `null`, the period **stacks**: `start = max(purchase.date, coverage_end)`, `end = start + duration`.
4. **Phases**: whenever the subscription is not covered at date `t` (coverage ended, or never started), and a phase is active at `t`, and `auto_renew` is true, and `t < cancelled_at` (if set), and `max_cycles` is not reached:
   - emit a charge on `t` for `price`,
   - emit a `paid` coverage period `[t, t + covers)`.
   If the phase starts after `coverage_end`, the first charge is on `phase.starts_on` (the gap is uncovered time).
5. Grants and phase renewals are interleaved chronologically: a grant purchased while a phase is running stacks after the current renewal, and the phase's next charge moves to the end of the stacked coverage.
6. Stop at the requested horizon (today for history, a future date for forecasting).

Past charges derived from phases are assumed to have happened as described. Future ones are projections.

## Derived computations

- **Is covered at date d**: some coverage period contains `d`.
- **Expiry date**: end of the last coverage period.
- **Next charge**: the next charge a running phase would emit (start of the first uncovered day), if `auto_renew` and not cancelled.
- **Cash cost over [a, b)**: sum of charges whose date falls in `[a, b)`. Bundles count their full price here (it is real money), but can be reported separately.
- **Amortized cost over [a, b)**: for each charge, take its cost basis (`allocated_amount` for bundles, `price` otherwise), divide it by the total number of days of the coverage periods it produced, and add the daily rate for every covered day inside `[a, b)`. Bonus and gift days produced by the same purchase lower the daily rate. A received gift (`price 0`) contributes nothing.
- **Effective monthly cost**: amortized cost over a calendar month.
- **Free days**: days covered by `bonus`, `included`, `trial` or `gift` periods, useful to report the value of promotions.

## How offers map onto the model

| Real-world offer | Model |
|---|---|
| 10 €/month, auto-renewed | 1 `Subscription` + 1 `BillingPhase { price 10, every {1, month} }` |
| Price increase | Close the current phase (`ends_on`), open a new one with the new price. Same subscription. |
| Pay 12 months, get 28 free | `Purchase { kind: prepaid_term, grants: [{12 month, paid}, {28 month, bonus}] }` |
| Buy an extension, 2 months included | `Purchase { kind: bundle, allocated_amount: 0 or fair value, grants: [{2 month, included}] }` |
| Gift card of X months while subscription is running | `Purchase { kind: gift, price 0, payer external, grants: [{X month, gift, starts_on: null}] }`. Stacks after current coverage; the next phase charge moves back by X months. |
| Gift card bought for yourself (e.g. discounted) | Same, with the real `price` and your `payer`. Amortized over the X months. |
| Free trial | `Purchase { kind: prepaid_term, price 0, grants: [{1 month, trial}] }`, or a phase with price 0 and `max_cycles: 1` followed by the paid phase |
| Intro promo (3 months at 0.99, then 9.99) | Phase `{ price 0.99, max_cycles 3 }`, then phase `{ price 9.99 }` starting when the first ends |
| Irregular period to align renewal dates | `Purchase { kind: prepaid_term, grants: [{4 month, paid}] }` |
| Refund or pro-rata credit | `Purchase { kind: refund or adjustment, price negative, grants: [] }` |
| Family plan shared by several users | `owner` = family, `service_users` = members, `payer` on each phase/purchase |

### Out of scope: money credit cards

A store credit card worth an amount (e.g. "25 € Apple / Battle.net balance") does **not** grant time. It is a balance that pays for future charges. It should be modeled as a payment method or wallet balance, not as a grant, so charges keep their normal price and the cost is recorded when the credit was bought. Not covered by this model yet.

## Validation rules

- Ids are unique per entity.
- `ends_on > starts_on` for phases; phases of one subscription do not overlap.
- Grant durations have `count > 0`.
- `allocated_amount` is only set on bundles and satisfies `0 <= allocated_amount <= price`.
- Negative prices only on `adjustment` / `refund`.
- Grants with an explicit `starts_on` that overlap existing coverage produce a **warning** (possible duplicate entry), not an error.
- A subscription with no phase, no purchase and no coverage is flagged as incomplete.

### Spotify with a price change and a gift card

```json
{
  "subscription": {
    "id": "sub-spotify", "provider_key": "s_spotify", "name": "Spotify Premium Duo",
    "owner": { "type": "family", "id": "family-1" },
    "service_users": ["user-a", "user-b"], "auto_renew": true
  },
  "billing_phases": [
    { "id": "ph-1", "subscription_id": "sub-spotify",
      "starts_on": "2024-06-28", "ends_on": "2025-06-28",
      "price": { "amount": 15.17, "currency": "EUR" },
      "every": { "count": 1, "unit": "month" },
      "payer": { "type": "family", "id": "family-1" } },
    { "id": "ph-2", "subscription_id": "sub-spotify",
      "starts_on": "2025-06-28", "ends_on": null,
      "price": { "amount": 17.20, "currency": "EUR" },
      "every": { "count": 1, "unit": "month" },
      "payer": { "type": "family", "id": "family-1" } }
  ],
  "purchases": [
    { "id": "pu-gift", "date": "2025-10-10", "label": "Spotify gift card 3 months",
      "kind": "gift", "price": { "amount": 0, "currency": "EUR" },
      "payer": { "type": "external" },
      "grants": [ { "subscription_id": "sub-spotify",
                    "duration": { "count": 3, "unit": "month" },
                    "source": "gift", "starts_on": null } ] }
  ]
}
```

Resulting timeline around the gift: paid until 2025-10-28, gift from 2025-10-28 to 2026-01-28, next charge of 17.20 € on 2026-01-28.

## Migration from the previous format

The previous format stored one record per period with `friendly_name`, `custom_price`, `start_date`, `end_date`, `recurrency` and `custom_recurrency`.

| Old | New |
|---|---|
| Several records for the same service | One `Subscription`, grouped by `provider_key` + `friendly_name` + `owner` |
| Record with `recurrency` monthly/quarterly/half_yearly/yearly/custom | `BillingPhase` with `every` = `{1, month}`, `{3, month}`, `{6, month}`, `{1, year}`, `{custom_recurrency, month}` |
| Record with `recurrency: one_time` and a start/end range | `Purchase { kind: prepaid_term }` with a `paid` grant matching the range |
| `custom_price` | `price` |
| `end_date` | `ends_on`, converted to half-open (inclusive ends like `2025-03-27` become `2025-03-28`) |
| missing `payer` | defaults to the owner |

Known data issues to review during migration:

- Duplicate ids across different periods (JetBrains `b426d65e…`, WoW `e90c2132…`).
- Overlapping Spotify records starting on 2023-08-28 (ending 2024-05-28 and 2024-06-28).
- WoW records with inconsistent price/period (a "1 Month" at 35.97 €, a "3 Month" at 12.99 €) and quarterly records spanning 15 months, probably year typos in `end_date`.
- `payer: { type: family }` without an id.
